## 录前操作卡（开录前 60 秒逐条打勾，2026-11-04 深夜实测）

1. **干净审计屏 = 新 session id**（开隐身窗；或 DevTools 删 `localStorage['payment.session.v1']` 后刷新）。
   `/session/reset` **不清审计**：审计是磁盘 JSONL（append-only），实测 reset 前 5 条 → reset 后仍 5 条。
   旧 id 上的历史 `plan_generated` 会永远挂在时间轴上，13 事件表就永远对不齐。
2. **后端启动必须带 `FRONTEND_BASE_URL`**（`apps/server/.env` 写的是 5173，Vite 实际在 3000，回跳会死链）：
   ```
   $env:FRONTEND_BASE_URL='http://localhost:3000'
   python -m uvicorn app.main:app --app-dir apps/server --host 127.0.0.1 --port 8000
   ```
3. **后端重启后不必手点 reset**：前端启动时 `GET /session/{id}/status`，`exists=false` 才创建会话
   （fix(web) 自动 materialize，不会误清已有会话）。看到"正在初始化会话..."是它在工作。
4. **F5 的边界**：只丢 `selectedPlanId` 与弹窗开关（React state）；约束/购物车/方案/订单在后端内存，
   审计在磁盘 → **F5 不丢流程**；**后端重启才丢**（session/订单），审计仍在。
5. **快照语义（本轮修复）**：方案在会话内首次 GET 生成一次，此后 5s 轮询只回放、不重算、不写审计。
   于是①审计里 `plan_generated` 只会有一条（反复开关方案 Tab = 0 条新事件）；
   ②加 350 不会把方案 B 改写成 350 —— 400 才打得出来。
6. **hook 镜头**：与团购主线共用同一个 id 也行（hook 不写团购审计/订单），但**别在正式镜头前 approve**（陷阱 E）。

## 285 改单分支（2026-11-04 深夜起 UI 可达；下方 API 写法与弹窗按钮等价，供彩排对照）

**弹窗内「🛒 购物车改单」执行的就是 `/cart/modify` 同一条指令**——预算拦截后确认键置灰，
改单成功自动解锁并切到新总价：

```
POST /api/v1/cart/modify?session_id=<sid>  {"instruction":"删掉木质相框、铝制奖牌、亚麻收纳袋"}
  → 393.0 → 285.0（5 件），审计 #10 cart_modified(ids=3)
POST /api/v1/paypal/create_order  {"session_id":<sid>,"amount":285.0,"user_email":"user@example.com",...}
  → 订单已 CONFIRMED：刷新快照为 285 → 预算门 285 ≤ 350 放行 → 200 + approval_url
  → 浏览器跳 approval_url → PayPal 批准 → capture → #12 payment_completed(285.0) → #13 paying→paid
```

- 这一步**不会**再写 `review_confirmed`（订单在第 7 步已 confirmed，复核不复写）——
  live 全链实测恰 1 条（`create#1` 400 → modify → `create#2` 200，`review_confirmed_count=1`）。
- **分摊同框自动变 95.00×3**：改单后弹窗自动重拉分摊 → 285/3 = 95.00（成员A/B/C，整除无尾差），
  不再是"只存在于 API 的弹窗#3"。

## 分摊真值表（2026-11-04 实测，弹窗逐格复核）

| 活跃约束 | 弹窗「每人应付」 | 说明 |
|---|---|---|
| 1 条（600） | **78.60 × 5** | `<2` 触发兜底五人（成员 A–E） |
| 2 条（600 + 350，source 均 user） | **196.50 × 2** | 名字显示 `user` ×2 |
| 3 条（600 + 350 + preference，source 均 user） | **131.00 × 3** | 名字显示 `user` ×3 |
| 3 条具名（成员A/成员B/成员C） | **131.00 × 3** | 名字正常；三等分整除 |

> API-only 尾镜头：同样三位具名成员、购物车 285 时，`split_preview` 返回 **95.00 × 3**（整除无尾差）。

成员数规则（`apps/server/app/api/cart.py:76`）：

```python
member_ids = [c.source for c in session.constraints if c.source and c.status == "active"]
if len(member_ids) < 2: member_ids = ["成员 A", "成员 B", "成员 C", "成员 D", "成员 E"]
```

→ **成员 = 活跃约束的 source（不去重，同名会出现多行）；只有 0/1 条约束时才兜底五人。**
所以"想加 3 个成员"只需凑够 3 条约束，**不需要**（也没法用）PaymentTab 的绿框。

## 五个现场陷阱（都实测过）

**陷阱 A · 生成时机——方案必须在收紧预算前生成（快照语义下更硬）。**
方案在会话内**首次 GET** 生成一次，此后约束变化不重算（`plans.py` 快照语义，2026-11-04 修复）。
所以：若开局就带 350，首次生成会把 B 组装到预算内 → **B = 350，400 不响**；
正确顺序是 600 先出方案（B=393），再加 350 —— 方案保持 393（5s 轮询也不会改写），
选 B 后购物车 393 > 350 → 门照拦 43.0。
（修复前旧行为：每次 GET 都重算 → 加 350 后 5s 内 B 变 350，400 在 UI 里永远打不出来。）

**陷阱 B · 弹窗#1 必须关闭，不能确认。**
先确认（600 预算下 393 合法）→ `create_order` 成功 → 订单进 PAYING 并拿到 approval_url；
此后加 350 再确认，命中 `paypal_callback.py:244-256` 的 PAYING 幂等分支，**原样返回同一
approval_url——预算门在它之后（`:294`）根本不会执行**。镜头会变成"超支照样付款"。

**陷阱 C · 别抄输入框建议语。**
「总预算 600 美元、5 人份」会被 LLM 抽成 **2 条**约束（budget 600 + functional 5.0）：
"5 人份"吃掉一个成员位、约束数 0→2；若三条都 source=user，弹窗变成 `user × N`。
镜头上念具名句式：「成员A说总预算 600 美元」。

**陷阱 D · 改单入口（已解除，2026-11-04 深夜）。**
历史版本：前端只有 `select_plan`/`split_preview`、无 `/cart/modify` 调用点，285 只能走 API（旧 trap D）。
现在确认弹窗内置「🛒 购物车改单」（自然语言指令 + 执行按钮），400 后同一弹窗内可改单重试。
**仍要注意 `select_plan` 会无条件重置购物车**（`cart.py:35`）——改完单后**别**再去点方案卡片
（否则 285 会被 393 覆盖），确认下单直接点弹窗里的按钮即可。

**陷阱 E · 预热会毁 HITL 镜头（approve 会抬高信任分）。**
支付 hook 的横幅写着"信任分随每次批准上升，高信任后小额自动放行"。若预热时点了 **approve**，
正式镜头里同一 `user_id` 可能**直接自动放行**——确认弹窗消失，"人做最终决定"的核心叙事没了。
预热最多点 **reject**；或干脆不预热：首腿实测 **200.7s**（冷启动新进程、新 id，`llm_source=real`），
等待用口播 talking points 填。**先查日志确认是慢不是挂**（uvicorn stderr 落在启动重定向的日志里）。

## hook 场景注记（30 秒判官路径，实测）

- **同 session 可拍**：`/payment/agent`、`/payment/approve` 不写团购审计、不写订单档案
  （实测 `audit total=0`、`orders count=0`，两轮；reject 后仍 0/0）。审计时间轴保持纯团购账本。
- **口播**：hook 证据在「💬 对话与支付」的**证据面板**（authority / evidence），
  **不要说"留在审计时间轴"**——那里没有它。
- **延迟**：首腿实测 **200.7s**（2026-11-04 深夜，冷启动新进程 + 新 id）/ 167.7s（冷）/ 85.2s（暖），
  `llm_source=real`。**240s 未返回那次是冷启动长尾或服务重启，不是挂死**——本次同配置 200.7s 正常
  返回 200。预热最多 reject（见陷阱 E）；等待用 talking points 填，别在镜头里空等。
- **第一腿没有 PayPal 按钮是正常的**：`needs_approval=true` 时 `approval_url` 为空，
  屏幕出现的是"确认 / 拒绝"卡；点 **确认** 之后才创建 PayPal 订单并拿到 `approval_url` → 才有支付按钮。
- **绿色框（现标签「🎯 储蓄目标」）= 储蓄目标入口**（`POST /payment/goal` → GoalMemory）：
  不写约束（0→0）、不写审计（0→0）、不写订单（0→0）；只让 `authority_check` 出
  `need_approval`，理由逐字命中目标约束。

## 取消分支（独立镜头，必须全新 session）

- **硬性要求：全新 session**（不要复用 paid 后的那个）。同 session paid 后再
  `create_order` 会返回 **409「订单已支付，禁止重复创建支付订单」**——这是预期的治理行为
  （防重复扣款），不是故障；镜头里若真出现，口播一句"同一会话不允许对已支付订单重复发起支付"
  即可，别慌。
- 步骤：新 session → 加预算 600 → 生成方案（A/B 数字同主线）→ 选方案 A/B → 支付
  → PayPal 页面点 **Cancel** → 落地页 `status=cancelled` → 订单状态 `cancelled`。
- 审计（同单）：`review_confirmed` → `draft→confirmed` → `confirmed→paying` → `paying→cancelled`。
- 取消后重建单（同 session 允许，CANCELLED 不再被复用）会**重新走一遍复核**——账本出现
  **第二次 `review_confirmed`**。这是好镜头：治理随订单重启，不留默认信任。
  → 操作细节：Cancel 回到落地页后**刷新前端**（`selectedPlanId` 归 null，方案按钮才恢复可点），
  再点「选择此方案」重开弹窗 → 确认 → PayPal 批准 → 第二笔进 `paid`。
- 一屏双终态：该 session 里最终两笔订单（`cancelled` + `paid`）并列在 OrdersTab，对比干净。

## Talking points（现场可背）

1. **393 复核叙事**："复核记录发生在 393 那一刻——用户确认了 393，预算门立刻把这笔超预算的
   支付拦下来；之后在同一笔订单上改单到 285（API 分支，见陷阱 D），服务端在支付前重新从购物车算价，
   PayPal 页面显示的就是 285。人看到多少、付多少、账本记多少，三者一致，这就是 HITL。"
2. **多预算取 min**："多条预算约束并存时，生效上限取最严格的一条——约束只会越收越紧，
   不会因为叠加而松动。"（`conflict_detected` 事件 + 看板冲突红框就是画面证据；实测
   600 vs 350 比例 1.7x 触发。）
3. **approval URL 透传**（K5 同步用）："the approval URL is relayed verbatim from the PayPal
   Orders API response; neither the agent nor the front end ever composes or rewrites it."
